# SauceDemo Web UI 自动化测试

![UI CI](https://github.com/jxyyxxx/sample-app-web-UI-test/actions/workflows/ui-ci.yml/badge.svg)

- 仓库地址：<https://github.com/jxyyxxx/sample-app-web-UI-test>
- 在线 Allure 报告：<https://jxyyxxx.github.io/sample-app-web-UI-test/>

这个仓库是我给开源的 SauceDemo 做的 Web UI 自动化测试。我对此项目做了测试侧：六层框架、10 个页面对象、24 条用例、Allure 报告体系、GitHub Actions 流水线。

动手之前我给自己定了三个标准：用例要能抓到真问题，功能坏了它得红，而不是只证明"页面能打开"；失败要能分流，一眼看出该找开发、查部署还是查用例；报告要能自证，同一套用例跑的是哪个版本的应用、第几次跑、全量还是冒烟，都得写在报告里。后面的设计基本都是围绕这三件事的取舍。

框架按六层分：配置、工具、页面对象、数据、用例、夹具与入口。分的依据不是功能齐全，是哪类东西会变就隔一层——页面结构变只改 `pages/`，断言规则变只改 `common/assert_utils.py`，账号变只改 YAML，用例本身几乎不动。代价很直接：读一条用例要跨两三个文件，24 条这个体量其实偏轻；我判断划算，是因为这个项目会继续加模块——最后补的三个动态目录页（滚动加载、loading 态、轮播）就只动了 `pages/` 和 `testcases/`。

选择器只认 `data-test`，不认 CSS 类名。类名属于样式实现，换主题、改布局都可能变；`data-test` 是应用留给自动化的接口，全项目用 `by_test_id()` 统一生成 `[data-test='...']`。有一个例外必须写清楚：侧边菜单按钮。应用源码把 `data-test='open-menu'` 写在自定义图标上，但 react-burger-menu 会把这个图标替换成一个纯文本按钮，真实 DOM 里根本没有这个属性——刚改成 data-test 那一次，登出和重置两条用例直接挂，查了 DOM 才发现。这里退回 `#react-burger-menu-btn`，代码里留了注释。

断言这块踩过一个"假通过"。排序用例最初是 `assert prices == sorted(prices)`，取一次快照比较；问题是列表异步重渲染，可能读到旧顺序——那不是偶发失败，是假通过，比红更危险。后来把"列表是否有序"写成一个 JS 判断，用 `wait_for_function` 轮询到成立为止，超时抛错时把实际顺序打出来。代价是这段 JS 要自己维护、报错信息要自己拼；好处是不会再出现"这次绿的，其实什么都没测到"。Playwright 的 Python 版没有 JS 里的 `expect.poll`，只能用 `wait_for_function` 实现同样语义。

24 条用例按风险分，不按页面凑：权限（登出后直接访问内页）、状态（Reset App State 后刷新仍为空）、金额（总额 / 税 / 应付三项分开断言）、表单（名 / 姓 / 邮编三条必填）、时序（滚动加载、loading 态、2 秒轮播）、移动端视口。冒烟挑了 3 条——登录、加购、完整下单，只覆盖主干；代价是反向场景进不了冒烟，只能等全量。登录态没有用 `storage_state` 复用，每条用例重新登录，全量因此多花约 20 秒，换来的是用例之间绝对干净；等用例上到 50 条再优化。

报告是花力气最多的一块。Allure 默认只有一屏通过率，我在上面加了五件事：环境面板（`BASE_URL`、浏览器、被测应用 commit、框架 commit 等 9 个字段，"这次红的是应用改坏了还是用例改坏了"看这里就能分流）、运行器标签（本地是「第 N 次 · 全量 24 条 · 开始时间」，CI 是「UI CI #123 · 全量 24 条」，趋势图每个点都有名字）、历史趋势、报告归档（每次的 HTML 报告存一份，PASS 留 20 份、FAIL 留 30 份，清理按目录名里的整数序号排而不是字符串——否则第 1000 次会排到 999 前面被误删）、失败分类（4 条规则按顺序首个命中：应用不可用 → 元素超时 → 断言失败 → 用例代码异常）。

失败现场除了全页截图，还把 Playwright trace 收进 `reports/traces/<第N次运行>/`，报告里附一条能直接粘贴的 `playwright show-trace` 命令。两个刻意的限制：只留最近 5 次（一次约 0.6 MB）、不进归档——归档是长期留存的成品，trace 是过程文件，混在一起只会让归档越滚越大。

CI 在 push / PR / 手动触发时跑：被测应用锁 commit 再 clone，不依赖线上站点，也不会因为上游改版让流水线自己变红；npm / pip / Chromium 都走缓存；启动后轮询到就绪才开始跑，超时先打应用日志再失败。报告只在 main 上发布到 Pages，PR 不覆盖线上。

## 用例清单（24 条）

| 模块   | 文件                                | 条数 | 覆盖内容                                                                                    |
| ---- | --------------------------------- | -- | --------------------------------------------------------------------------------------- |
| 登录   | `login/test_login.py`             | 5  | 标准用户登录成功（并校验 `session-username` cookie）、锁定用户被拒、密码错误、用户名为空、登出后直接访问内页被拦回登录页               |
| 商品列表 | `inventory/test_inventory.py`     | 7  | 加购 1 件角标为 1 且按钮变 Remove、加购 2 件且购物车商品正确、价格升序 / 降序、名称 A→Z、详情页与列表一致、Reset App State 后刷新仍为空 |
| 购物车  | `cart/test_cart.py`               | 1  | 移除商品后购物车为空、角标消失、回列表按钮恢复为 Add to cart                                                    |
| 结算   | `checkout/test_checkout.py`       | 5  | 完整下单、缺名 / 缺姓 / 缺邮编各一条提示、总额 + 税额 + 应付三项与购物车一致                                            |
| 动态目录 | `catalog/test_dynamic_catalog.py` | 5  | 滚动到底部追加加载、卡片由占位符转真实内容、loading 圈替换为网格、点圆点切换商品、每 2 秒自动轮播                                  |
| 兼容性  | `compat/test_compat.py`           | 1  | 移动端视口 390×844 下登录并加购                                                                    |

标记：`smoke`（登录成功 + 加购 + 完整下单，共 3 条）、`login`、`inventory`、`cart`、`checkout`、`catalog`、`compat`。
